# T05 katas

## 1. Why `usage_by_model` cannot take `&[String]` and parse inside

The return type is `BTreeMap<&'a str, Usage>`: the keys are borrowed model
names that point into the `serde_json::Value`s. If the function took
`&[String]` and called `serde_json::from_str` itself, the parsed `Value`s
would be locals owned by the function and dropped when it returns, so a key
borrowing from one would dangle. The `'a` in the signature is the promise that
the keys live as long as the caller's `Value`s, and the caller is the only one
who can own those long enough. To parse inside you would have to return
`BTreeMap<String, Usage>` and clone every model name.

## 2. The item type of the `flat_map`

`flat_map` takes `F: FnMut(Self::Item) -> U` where `U: IntoIterator`, and the
resulting iterator's item is `U::Item`. The closure returns `Vec<Input>`, and
`Vec<T>` implements `IntoIterator<Item = T>` (through `vec::IntoIter`), so the
`flat_map` yields `Input`. Any `IntoIterator` would do, which is why an
`Option<Input>` would also qualify.

## 3. `then` versus `then_some`

`cond.then_some(event(..))` evaluates `event(..)` before the call, whether
`cond` is true or false, because function arguments are evaluated eagerly.
`cond.then(|| event(..))` only runs the closure when `cond` is true. So
`then_some` is the one that evaluates `event` when `cond` is false. In
`assistant_line` the lazy form is the right one: it avoids building a
`TurnEnded` event that is immediately thrown away.
