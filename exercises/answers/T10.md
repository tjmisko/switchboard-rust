# T10 katas

## 1. Why must `wake` be rebuilt every pass?

Because the deadline it sleeps towards is a property of the board, and the
board changes on every input. A turn starting adds a `TURN_STALE` deadline;
an inferred escalation adds a `promote_at`; a `Stop` adds wait expiries. If
`wake` were built once above the loop it would hold the deadline as it was
before the first input, which is usually `None`, so the future would be
`pending()` forever and the core would never tick: no dwell would ever
promote, no stale turn would ever end. Even with a real first deadline, the
loop would keep waking at a stale instant (or, after the first wake, at an
instant already in the past, spinning) instead of the earliest one the board
now has.

There is also a mechanical reason: `select!` takes the future by value, so a
`wake` declared outside the loop would be moved on the first pass and the
second pass would not compile (use of moved value). You could `pin!` it and
pass `&mut wake`, but then you would be re-polling a completed `Sleep`, and
you would still have the stale-deadline problem above.

## 2. What does `async move` capture, and why is that cheap?

It captures `deadline: Option<std::time::Instant>`, by value. `Instant` is
`Copy` and 16 bytes, so the capture is a copy of an `Option` of two words,
no allocation and nothing borrowed from `board`. That last part matters more
than the size: because the future owns a copy rather than a `&Board`, it does
not hold a shared borrow of the board across the `select!`, and the other arm
is free to take `&mut board` for `reduce::apply`. Without `move`, the block
would borrow `deadline` (fine, it is a local) but the temptation is to write
`next_deadline(&board)` inside the block, and that borrows the board for the
future's whole life, which conflicts with the `apply` arm.

Once polled, the future also owns the `Sleep` it created, but that is created
inside the future, not captured.

## 3. `watch` versus `broadcast`

`broadcast` is a queue per receiver with a fixed capacity. A slow subscriber
falls behind; when the queue fills, the oldest values are overwritten and its
next `recv()` returns `RecvError::Lagged(n)` telling it how many it missed. It
must then decide what to do about the gap, and every value sent is retained
until the slowest receiver has taken it, so a stuck subscriber pins memory up
to the capacity.

`watch` keeps only the latest value. A slow subscriber wakes once, calls
`borrow_and_update()`, and sees the newest view; the intermediate views it
never looked at simply do not exist for it. There is no queue to fill, so
there is no `Lagged` error and no memory held for a stuck subscriber. The
failure `watch` makes impossible is "a subscriber sees a stale intermediate
state, or has to handle a lag error, when all it wanted was the current
state". The view is a state, not an event stream, so skipping intermediates
is correct rather than lossy; effects are an event stream, so they go on an
`mpsc` where nothing may be skipped.
