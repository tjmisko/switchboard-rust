# T12 katas

## 1. The `Arc<Mutex<..>>` version of `poll_once`, and two things that got worse

Sketch:

```rust
let state: Arc<Mutex<Option<(File, Tail)>>> = Arc::new(Mutex::new(None));
loop {
    ticker.tick().await;
    let state = Arc::clone(&state);
    let path = spec.path.clone();
    let polled = tokio::task::spawn_blocking(move || {
        let mut guard = state.lock().unwrap();
        poll_once_in_place(&mut *guard, &path, replay)   // fn(&mut Option<(File, Tail)>, ..) -> Option<Polled>
    })
    .await;
    ...
}
```

What got worse:

1. **A lock is held across blocking file I/O to protect something only one
   party ever touches.** Nobody else can lock it (the async side never
   does), so the mutex does no work, but the compiler can no longer tell
   you that. With the by-value version, `poll_once(state: Option<..>) ->
   Option<..>` says in its signature that the caller gave up the state and
   gets it back; single ownership is checked at compile time instead of
   enforced at runtime.
2. **Poisoning and a new failure mode.** If `poll_once` panics while the
   guard is held (a `seek` on a closed handle, an assertion), the mutex is
   poisoned and every later `lock()` returns `Err`. The by-value version
   has no such state: a panic in the blocking closure surfaces as a
   `JoinError` and the `Option` was simply never handed back, so the next
   tick reopens.

Also worse, but smaller: an allocation and two atomic refcount operations
per tick; `poll_once` is no longer a plain function you can unit-test with
a `Cursor` and a `Tail`; and `std::sync::MutexGuard` is `!Send`, so the
moment someone writes an `.await` inside the closure's scope by mistake the
error is the same distant "future cannot be sent" from T11.

## 2. `abort` on a watcher that is inside `spawn_blocking(..).await`

`JoinHandle::abort` cancels the *async* task: at its next poll the runtime
drops the future instead of resuming it. The future is currently suspended
on the `JoinHandle` of the blocking task, so that inner handle is dropped.
Dropping a blocking task's `JoinHandle` **detaches** it; it does not stop
it. There is no way to interrupt a thread that is inside `read` or `seek`.

So the blocking closure runs to completion on the blocking pool. It owns the
`File` (it was moved in as `taken`), reads what is new, and returns
`(Some((file, tail)), Some(polled))` to a `JoinHandle` nobody will ever
await. The runtime drops that result, and that is when the `File` closes:
shortly after the abort, not at it. Nothing leaks, because ownership was
always in exactly one place and that place is dropped. Nothing is sent
either: the `inbox.send` calls come after the `.await`, and the future never
resumes past it. If the closure had not started yet, tokio's `abort` on a
not-yet-started blocking task does cancel it, and then the `File` (inside
`taken`) is dropped without ever being read.

The one cost is the blocking pool thread finishing a poll whose result is
thrown away, bounded by one read of at most the file's growth since the
last tick.

## 3. Why a recycled pid is both a death and a birth, and what breaks with pid-only keys

`known` holds `{pid: 5, start: 100}`. The sweep returns a row with
`{pid: 5, start: 200}`. The `BTreeSet` difference `known \ seen` is
`{5, 100}`, so one `Died` is emitted for the old key, and the snapshot
carries `{5, 200}`, which the reducer has never seen, so `discovered`
treats it as a new agent: `AgentFound`, `WatchTranscript`, a fresh
`Agent` with `Activity::Unobserved`. Two different processes, two
different keys, two different fates in one sweep. The order matters too:
the snapshot goes first, so the board learns the new process before it is
told the old one died, and the `Died` routes by full key, so it cannot hit
the newcomer.

If `ProcKey` were just the pid:

- The set difference is empty. The old agent's death is never observed.
  No `AgentLost` in history, no `Forget`, no watcher stopped.
- The snapshot merge finds an existing agent with pid 5 and updates its
  row fields (cwd, tty, cpu). The new process inherits the old agent's
  session, turn, gates, waits and `Shown` phase. A brand-new `claude`
  might render as `Blocked` on a permission prompt that belonged to a
  process that no longer exists, which is the exact false-red the cost
  model exists to prevent, and the transcript watcher for the new session
  might never start because the agent "already has" one.
- The old transcript watcher keeps polling the old file under the same
  key; when the new session is finally learned from a hook, `start`
  aborts it, but until then its lines are attributed to the new process.
- A late `Died` (or a hook from the dead process still in flight) would be
  routed to whichever process now holds the pid and kill or mutate the
  wrong agent. The scanner's ordering guarantee ("a sweep can never land
  after the death of a process it contains") is only meaningful because
  the keys are distinct.
