## 0. `route` as `-> Option<&mut Agent>` (the sheet's experiment)

```rust
pub fn route_mut<'b>(board: &'b mut Board, process: Option<ProcKey>, session: &SessionId) -> Option<&'b mut Agent> {
    process
        .and_then(|key| board.agents.get_mut(&key))
        .or_else(|| board.agents.values_mut().find(|a| a.session.as_ref() == Some(session)))
}
```

```
error[E0524]: two closures require unique access to `board.agents` at the same time
  --> src/reduce/mod.rs:75:18
   |
73 | /     process
74 | |         .and_then(|key| board.agents.get_mut(&key))
   | |                   ----- ------------ first borrow occurs due to use of `board.agents` in closure
75 | |         .or_else(|| board.agents.values_mut().find(|a| a.session.as_ref() == Some(session)))
   | |__________________^^_------------_______________- returning this value requires that `board.agents` is borrowed for `'b`
   |                    second closure is constructed here
```

Both closures capture `board.agents` by unique borrow, and the first one's
result (an `Option<&'b mut Agent>`) has to live for `'b` because it is
returned, so the `&mut` it took is still alive when the second closure is
built. An `if let ... else` chain instead of combinators runs into the same
wall in a different costume (the "conditional return of a borrow" case NLL
still rejects). Returning the `Copy` key sidesteps it: the search borrows
`board` shared and briefly, and the caller does one `get_mut` afterwards.

## 1. `tools` and reassigning `agent.activity`

Inside `if let Activity::Turn { tools, .. } = &mut agent.activity`, `tools`
is a `&mut BTreeMap` that borrows *through* `agent.activity`. Non-lexical
lifetimes end that borrow at the last use of `tools`. If the last use is
before the assignment, the borrow is over when `agent.activity = idle(..)`
runs, so assigning is fine: nothing is looking at the old value any more.
If you then read `tools.len()` after the assignment, the borrow has to stay
alive across the assignment, and the assignment would overwrite the enum
whose field `tools` points into, so the compiler rejects the assignment
(E0506, "cannot assign to `agent.activity` because it is borrowed"). The
rule is not about the `if let` block; it is about whether `tools` is used
again afterwards.

## 2. Cloning the outcome in `end_turn`

`apply_event` owns `event`, but it passes `&event` to `transition`, which
matches on `&event.kind` and hands `end_turn` a `&TurnOutcome`. To move the
outcome you would have to match on `event.kind` by value, which means
`transition` takes `Event` (or `EventKind`) by value, and then `apply_event`
can no longer use `event.cause`, `event.confidence` or `event.session`
afterwards unless it copies them out first (they are `Copy` or cheap, so
that part is fine). `end_turn` would take `TurnOutcome` by value, and the
`ToolSettled{Failed{interrupt: true}}` arm, which builds its own
`Interrupted` outcome, would be unaffected. It is not worth it: the outcome
is at most a `Box<str>`-sized `MessageId` clone, once per turn end, and the
by-reference `transition` lets every arm read the event's other fields
freely and lets `subagent_transition` share the same `&Event`.

## 3. `settle(agent, limits_for(accounts, agent), ..)`

Two-phase borrows: the `&mut agent` for the first argument is taken as a
"reservation" and only activated when the call happens, so evaluating the
second argument may still borrow `agent` shared. `limits_for`'s signature is
what makes the result usable: it returns `Option<&'a Limits>` with `'a`
tied to `accounts`, not to `agent`, so the returned reference does not keep
`agent` borrowed once the argument is evaluated. Binding `let limits =
limits_for(accounts, agent);` first is clearer because the reader sees that
`limits` outlives no borrow of `agent`, and it would still compile if
two-phase borrows did not exist. If `limits_for` instead returned something
borrowing from `agent`, the binding would not help: the shared borrow would
overlap the `&mut` for the whole call.
