# T11 katas

## 1. Why generic halves, and what `Unpin` has to do with `.read()` / `.write_all()`

Taking `R: AsyncRead + Unpin, W: AsyncWrite + Unpin` instead of a
`UnixStream` means the test can hand `handle` two ends of
`tokio::io::duplex`: an in-memory pipe with no socket file, no `bind`, no
`accept`, no permissions, and no cleanup. It also lets `serve` pass the two
halves of `into_split()` (`OwnedReadHalf`, `OwnedWriteHalf`) so the read side
can be wrapped in `take` and `BufReader` while the write side stays a plain
sink, and both are owned so the handler can be `tokio::spawn`ed. Every test
except the end-to-end one uses the duplex path.

`Unpin`: the convenience methods on `AsyncReadExt` / `AsyncWriteExt` are
declared `fn read(&mut self, ..) -> Read<'_, Self> where Self: Unpin` (same
for `write_all`, `flush`, and `Lines::next_line`). The futures they return
hold `&mut Self` and, when polled, must call the trait's `poll_read(self:
Pin<&mut Self>, ..)`. Going from `&mut Self` to `Pin<&mut Self>` is
`Pin::new(&mut *self)`, and `Pin::new` is only sound when `Self: Unpin`,
because it promises the value will not move and a `&mut` to an `!Unpin` type
would let you `mem::swap` it. Without the `Unpin` bound you would have to
pin the reader yourself (`tokio::pin!` or `Box::pin`) and use the raw `poll_*`
API. Sockets, duplex streams and their split halves are all `Unpin`, so the
bound costs nothing here and buys the ergonomic `.await`able methods.

## 2. Holding `let r = view.borrow();` across `spawn_blocking(..).await`

Two different problems depending on where the future ends up.

If the future is spawned (`tokio::spawn(handle(..))` in `serve`, or the
test's `connect`), it is a **compile error**: `tokio::spawn` requires
`F: Send`, and a `watch::Ref` wraps a `std::sync::RwLockReadGuard`, which is
`!Send` (a guard must be released on the thread that took it). The error
message points at the `tokio::spawn` call site, not at the borrow, and says
"future is not `Send` as this value is used across an await". I checked:
that is exactly what you get if you write `snapshot_line(&view.borrow())`
inline inside a `write_line(..).await` argument, because the temporary lives
to the end of the statement.

If the future is not spawned (awaited directly inside `block_on`, or inside
a `LocalSet`), it compiles, and it is a **runtime problem**: the read guard
stays held for the whole `/proc` walk on the blocking pool. Meanwhile the
core's next `send_if_modified` takes the write lock, and `std::sync::RwLock`
blocks the OS thread synchronously, so the core task stalls a worker thread
for as long as the blocking task takes, and every other task on that worker
with it. That is the "never await anything that can stall" rule broken from
the other side. Copying the keys out into a `Vec` before the `.await` makes
the guard's lifetime one statement long.

## 3. `send().await` instead of `try_send` with a slow core and ten agents

The inbox is a bounded channel (4096 by default). While it has room, `send`
returns immediately and nothing changes. The chain starts when the core is
slow enough that the inbox is full:

1. Ten hooks fire; ten forwarders connect; ten connection tasks decode the
   frame and call `send(input).await`. All ten park on the channel.
2. Each forwarder is blocked in `read_line` waiting for `{"ok":true}`, which
   the handler only writes after `send` returns. The agent's hook runs the
   forwarder synchronously, so each of the ten agents is now paused inside
   its hook.
3. Every time the core drains one slot, one parked task wakes, sends, and
   replies. The other nine keep waiting. If the core is slow, most of the ten
   hit the forwarder's 500 ms timeout first: `read_line` fails with a timeout
   `io::Error`, the forwarder returns `ForwardError::Io`, and the agent
   resumes. The agent was stalled for the full 500 ms. Hooks fire several
   times per tool call, so a slow core turns into a visible slowdown of
   every agent on the machine, which is the one thing the design says the
   daemon must never do.
4. The parked connection tasks do not know the forwarder gave up. They still
   deliver the input when the core catches up, then try to write a reply to
   a closed pipe, get a broken pipe error, and exit. So nothing is lost, but
   the daemon spent 500 ms of ten agents' time to deliver late what the
   transcript watcher would have recovered anyway.

With `try_send` the connection task drops the input on a full inbox, logs
once, and replies `ok` immediately. The forwarder returns in microseconds,
the agent never notices, and the dropped hook is repaired by the transcript
replay. The daemon's slowness stays the daemon's problem.
