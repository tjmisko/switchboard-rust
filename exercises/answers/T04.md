# T04 katas

## 1. `BufReader::new(file.take(n))` with `file: &mut R`

The impl is std's blanket `impl<R: Read + ?Sized> Read for &mut R`. So
`&mut R` is itself a reader, and `Read::take(self, n)` is called with
`Self = &mut R`.

Because the receiver is a `&mut` reference, the method call does not move
`file`: the compiler inserts an implicit reborrow, `(&mut *file).take(n)`.
The resulting `Take<&mut R>` holds that reborrow, and the `BufReader` around
it holds the `Take`. While the `BufReader` is alive, `file` is mutably
borrowed and cannot be touched.

When the `BufReader` is dropped, the reborrow ends and `file` is usable
again. Two caveats: any bytes the `BufReader` read into its buffer but never
handed out are gone (the underlying position has moved past them), which is
why `poll` bounds the read with `take` and reads to the end; and if you had
written `let f = file; f.take(n)` or passed `file` into a generic
`fn(R)` that takes `R` by value, the `&mut R` itself would move and `file`
would be dead. The reborrow only happens where the expected type is visibly
`&mut _`.

## 2. `lines()` needs `BufRead`

`lines` is defined on `BufRead`, not `Read`. `File` implements only `Read`:
every call is a `read(2)` syscall into whatever buffer you pass, and there
is no way to look ahead for a `\n` without consuming. `BufReader<File>`
adds an internal buffer and implements `BufRead` through `fill_buf` and
`consume`, so `read_line` can scan the buffered bytes for the delimiter, hand
back exactly one line, and leave the rest for the next call.
`std::io::stdin()` works because `Stdin::lines` locks stdin and the locked
handle is already buffered (`StdinLock: BufRead`).

Hand-rolling byte-at-a-time `read` on a `File` costs one syscall per byte.
A syscall is hundreds of nanoseconds to a microsecond of kernel transition
plus the read itself, so a 1 MiB transcript line becomes a million syscalls
instead of the ~128 reads of 8 KiB that `BufReader` makes. Throughput drops
by two to three orders of magnitude, and the work is all overhead.

## 3. `HistoryWriter::new(&mut file)` versus `HistoryWriter::new(file)`

`HistoryWriter<W: Write>` is generic, and `&mut File` implements `Write`
through the same kind of blanket impl as in kata 1.

`HistoryWriter::new(&mut file)` in a loop makes `W = &mut File`. The writer
*borrows* the file for as long as the writer lives; ownership stays with the
caller. Each iteration's writer is dropped at the end of the body, the borrow
ends, and the next iteration can borrow again. After the loop, `file` is
still the caller's, which is why the test can `file.write_all(b"\n")`
directly.

`HistoryWriter::new(file)` makes `W = File`. The `File` is *moved* into the
writer; `file` is no longer usable by name, and the descriptor is closed when
the writer is dropped unless the caller takes it back with `into_inner`.
Same code, two different `W`s, two different ownership stories.
