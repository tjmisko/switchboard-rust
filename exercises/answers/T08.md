# T08 katas

## 1. `position` then `remove`, not `find` then remove

`iter().find(..)` hands back `Option<&Unjoined>`: a shared reference into
the vector. You cannot move an `Unjoined` out through a `&`, and while that
reference is alive you cannot call `remove` on the vector either, because
`remove` needs `&mut self`. You would have to clone the found element, drop
the reference, then search again to find its index. `position` returns a
`usize`, which is `Copy` and borrows nothing, so the search borrow ends
immediately and `remove(i)` can take `&mut` and hand the element back by
value. The index is the only thing you can carry across the borrow.

## 2. `or_insert_with(|| Tool { .. })` versus `or_insert(Tool { .. })`

`or_insert(value)` evaluates its argument before the call, so the `Tool`
would be built on every `ask`, including the common case where the call
already exists and the value is thrown away. That construction clones the
`ToolName` and, if the hash is missing, builds a placeholder. The closure in
`or_insert_with` runs only on the vacant branch, so nothing is allocated
unless the entry is actually inserted. Both return `&mut Tool`, and the
laziness is the only difference. It is the same distinction as kata 3 of T05
(`then` versus `then_some`).

## 3. The one line in `end_turn`

```rust
let lifted = clear_unjoined(&mut agent.prompts, &Actor::Agent);
```

The `&Actor::Agent` argument. `clear_unjoined` retains every prompt whose
actor differs, so a prompt parked under `Actor::Subagent(id)` survives the
agent's `Stop`. A subagent's *joined* gate is never at risk from `end_turn`
at all: it lives in `agent.subagents.rows[id].gate`, and `end_turn` only
writes `agent.activity` and `agent.prompts`.

## 4. Two identical `AskUserQuestion` calls and a third call-less ask

Claude announces one question twice: `PreToolUse` with the call id, then
`PermissionRequest` without it, for the same input. When both open calls
are already `Blocked` on that `(tool, hash)`, the id-carrying announcement
has already gated each of them, so a call-less announcement for that input
can only be the second half of one of those pairs. Treating it as a third
gate would park a prompt that nothing will ever settle by id: the answer
arrives as `PostToolUse` with the call id, which removes the call but leaves
the parked prompt, and the chip stays red after the operator has answered.
That is exactly the contradicted-calm bug the cost model calls the most
expensive in the system.

A *running* identical call is different evidence: it has not been gated by
anything yet, so a call-less prompt for its `(tool, hash)` is the only
announcement it will get (a plain `Bash` call gets no id-carrying gate
event). The prompt must attach to it, or the agent that is genuinely
waiting on a human shows green. Preferring running over blocked is what
lets the same rule serve both cases.
